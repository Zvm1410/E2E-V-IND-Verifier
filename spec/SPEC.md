# SPEC.md

Cryptographic audit framework for end-to-end verifiable voting in air-gapped electronic voting machines.

Specification version `v1`, revision 3. Owners: basket B and basket D jointly; from revision 3 basket D holds sole editorial authority.

Revision 2 changes no preimage, no field, no field order and no byte encoding. Every domain separation label stays at `-v1` and every hash in the system is unchanged. See the change log in section 20.

## 0. Status and change control

This document is frozen at the end of day 1. After that, no change is made by one person editing this file. A change is proposed to the group, agreed, applied here, announced, and the version label in every affected domain separation string is incremented. A local patch that is not written here means two implementations now differ and nobody knows which is right.

Basket D implements from this document and from `spec/vectors/`. Basket D does not read `crypto/` or `tally/` source. If something here is ambiguous, D asks B or C, and the answer is written into this file rather than delivered verbally.

Everything below is normative. Where a byte order, a field order, or a padding rule is stated, it is not a suggestion.

## 1. Conventions

`p`, `q`, `g` are the group parameters of section 2. `G` is the subgroup of order `q` generated by `g`.

Group elements are integers in `[1, p)`. Exponents, challenges and responses are integers in `[0, q)`. Mixing these is the single most common bug in this kind of code. Exponents live modulo `q`. Elements live modulo `p`.

`m` is the number of candidates including NOTA. Candidate indices are `0` to `m - 1` in configuration order. `n` is the number of trustees, `t` the decryption threshold. `N` is the number of ballots issued at a booth.

Concatenation of byte strings is written `||`.

## 2. Group parameters

The group is RFC 3526 group 15, the 3072-bit MODP group.

```
p = 2^3072 - 2^3008 - 1 + 2^64 * ( floor(2^2942 * pi) + 1690314 )
q = (p - 1) / 2
g = 2
```

`p` is a safe prime, so `q` is prime and `g` generates a subgroup of order `q`. Because `p ≡ 7 (mod 8)`, the integer 2 is a quadratic residue modulo `p`, and therefore `g^q ≡ 1 (mod p)` holds with `g = 2` as published by RFC 3526. No substitute generator is needed.

Implementations hard-code `p` as a literal. Do not recompute it from the formula at runtime. The literal is checked on load against these pinned values:

```
bit length of p                     3072
first 64 hex digits of p            FFFFFFFFFFFFFFFFC90FDAA22168C234C4C6628B80DC1CD129024E088A67CC74
last 32 hex digits of p             4B82D120A93AD2CAFFFFFFFFFFFFFFFF
bit length of q                     3071
SHA-256 of I2B(p)                   48cf8b092fbce4359d9871abf74f98e25b6163379eaa15cd9087e800c6d1c55c
SHA-256 of I2B(q)                   018089836b3704979e9c4ed47a717e61440ff98b4deba0e7e95e56514442e52c
SHA-256 of I2B(g)                   0c29b032a70f848d7ce809f1c926afaea4bce7b3a037ad74b39861c19eb0161c
```

Load-time assertions, run by B, C and D independently in their own code:

1. `p` and `q` are prime under Miller-Rabin with at least 32 rounds.
2. `p == 2 * q + 1`.
3. `pow(g, q, p) == 1`.
4. `p % 8 == 7`.
5. The three SHA-256 digests above match.

### 2.1 Subgroup membership

Membership in `G` is defined as:

```
in_group(x)  iff  0 < x < p  and  pow(x, q, p) == 1
```

Since `q = (p - 1) / 2`, this is exactly the Legendre symbol test, and it costs one modular exponentiation.

The verifier applies `in_group` to every group element it parses from the board, without exception: ciphertext components, commitments, proof commitments, trustee commitments, partial decryptions, and the election public key. An element of order 2 accepted into a ciphertext breaks the soundness argument of the validity proof. This check is not optional and it is not a formality.

Two things about the definition, because both have been got wrong before.

The exponentiation test alone is what rejects order 2. The unique element of order 2 is `p - 1`, and since `q` is odd, `(p-1)^q ≡ (-1)^q ≡ -1 ≡ p - 1 (mod p)`, which is not 1. The lower bound is not doing that work and must not be justified by it.

The lower bound is `0 < x`, not `1 < x`. The identity is a legitimate member of `G`, consistent with section 1, and honest values can equal it: a proof commitment `a_d = g^{f_d} · alpha^{-c_d}` is 1 whenever `f_d ≡ r·c_d (mod q)`, which no choice of sampling range can exclude. Rejecting the identity here would make clean-mode false rejection nonzero in principle, which section 16 forbids. Where the identity is genuinely not acceptable, namely a ciphertext component, it is excluded by an explicit named check in section 8.3 rather than by folding it into `in_group`.

The verifier applies a range check `0 <= x < q` to every challenge and every response it parses.

## 3. Encoding

### 3.1 Integers to bytes

```
I2B(x)  =  x encoded big-endian, zero-padded on the left, exactly 384 bytes
B2I(b)  =  int.from_bytes(b, "big")
```

384 bytes applies to group elements and to exponents alike, even though `q` is one bit shorter than `p`. Fixed width means fixed width. `I2B(1)` is 383 zero bytes followed by `0x01`. A value that happens to begin with zero bytes still occupies 384 bytes.

### 3.2 Small integers

Counts, indices, serials and rates are encoded as unsigned 8-byte big-endian, written `U64(x)`.

### 3.3 Strings

`booth_id` is ASCII, at most 32 bytes, encoded UTF-8 and right-padded with `0x00` to exactly 32 bytes. Written `S32(x)`.

`election_id` and `candidate_id` are UTF-8, at most 64 bytes, right-padded with `0x00` to exactly 64 bytes. Written `S64(x)`.

### 3.4 Domain separation labels

```
L(s) = ASCII bytes of s, right-padded with 0x00 to exactly 32 bytes
```

Every label is used at exactly one place in the system. The complete list:

```
EVOTE-BASE-v1          base hash
EVOTE-VALIDITY-v1      per-candidate validity proof challenge
EVOTE-SUMONE-v1        sum-to-one proof challenge
EVOTE-RCOMMIT-v1       pre-poll randomness commitment
EVOTE-TESTSCHED-v1     test schedule commitment
EVOTE-TESTDRAW-v1      test schedule per-ballot draw
EVOTE-PARTIAL-v1       partial decryption proof challenge
EVOTE-BOARD-v1         board digest
EVOTE-SIG-v1           signature message prefix
```

### 3.5 Integers in JSON

Group elements and exponents appear in JSON as lowercase hexadecimal strings of exactly 768 characters, that is `I2B(x).hex()`. They are never JSON numbers. JSON numbers are used only for small integers that fit in 32 bits: counts, indices, thresholds.

This type is referred to below as `HEX384`. A parser that accepts a `HEX384` field of any length other than 768 rejects the board.

## 4. Hashing

All hashes are SHA-256.

A challenge is computed as:

```
challenge = B2I( SHA-256(preimage) ) mod q
```

SHA-256 produces 256 bits and `q` is 3071 bits, so the reduction is the identity map. It is specified anyway so that both implementations perform the same operation. The effective challenge space is 2^256, which is the security level of the Fiat-Shamir transform here.

Every preimage below is written out field by field, in order. The total byte length is stated. If your preimage is not that length, stop and find the missing field before doing anything else.

## 5. Election configuration and the base hash

### 5.1 config/election.json

```json
{
  "election_id": "SPACE2026-DEMO",
  "booth_id": "BOOTH-001",
  "candidates": [
    {"index": 0, "candidate_id": "CAND-A"},
    {"index": 1, "candidate_id": "CAND-B"},
    {"index": 2, "candidate_id": "CAND-C"},
    {"index": 3, "candidate_id": "CAND-D"},
    {"index": 4, "candidate_id": "CAND-E"},
    {"index": 5, "candidate_id": "NOTA"}
  ],
  "trustees": {"n": 5, "t": 3},
  "authorities": {"agents": 4, "k": 2},
  "test_rate": {"num": 1, "den": 20},
  "ballots_expected": 200,
  "seed": 20260804
}
```

The candidate list is identical across booths. NOTA is the last entry and is an ordinary candidate index for all cryptographic purposes.

`test_rate` is a rational number given as two integers. Floating point never appears in any hashed or serialised value.

`seed` drives every deterministic draw in a simulated run. In a real deployment the randomness sources named in section 10 come from `secrets`; the seeded path exists so that run 4,417 of 10,000 can be reproduced exactly.

Malformed configuration produces one clear error message naming the missing or invalid field. Basket A owns this loader.

### 5.2 Base hash Q

`Q` is 32 raw bytes, computed once, before the poll opens, after trustee setup. It binds every downstream proof to this election, this group, this candidate list, this trustee set and this set of signing authorities. It is what makes section 8's strong Fiat-Shamir binding cheap to state and cheap to check.

```
Q = SHA-256(
      L("EVOTE-BASE-v1")                      32
      I2B(p)                                 384
      I2B(q)                                 384
      I2B(g)                                 384
      S64(election_id)                        64
      U64(m)                                   8
      S64(candidate_id[0]) .. S64(candidate_id[m-1])    64 * m
      U64(n) U64(t)                           16
      I2B(pk)                                384
      I2B(h_1) .. I2B(h_n)                   384 * n
      U64(number_of_agents) U64(k)            16
      officer_ed25519_public_key              32
      agent_ed25519_public_key[0..a-1]        32 * a
    )
```

Total length is `1704 + 64m + 384n + 32a` bytes. For the default configuration, `m = 6`, `n = 5`, `a = 4`, that is `1704 + 384 + 1920 + 128 = 4136` bytes.

The fixed part is `32 + 384 + 384 + 384 + 64 + 8 + 16 + 384 + 16 + 32 = 1704`. Earlier revisions of this document said `1696` here, which is one `U64` field short and gives `4128`. The field list above is and always was correct; the summary sentence was stale. If an implementation computes 4128, it is missing a field, not disagreeing about a total.

`Q` appears in every challenge preimage in the system. `booth_id` is not inside `Q`, because one election configuration may be run at several booths; `booth_id` is carried separately in each preimage that needs it.

## 6. Keys and trustee setup

A trusted dealer generates the election key. This is a deliberate simplification of Pedersen distributed key generation. It changes nothing that the verifier checks, and it is stated in the paper rather than hidden.

```
sk  <- uniform in [1, q)
pk  =  g^sk mod p
```

Sharing is Shamir over the field of integers modulo `q`.

```
P(X) = sk + a_1 X + ... + a_{t-1} X^{t-1}   (mod q),  a_j uniform in [0, q)
share s_j = P(j) mod q,  for j = 1..n
commitment h_j = g^{s_j} mod p
```

The dealer publishes `pk` and `h_1 .. h_n` on the board and destroys `sk` and the coefficients. The shares go to the trustees and never appear on the board or in any exported file.

Lagrange reconstruction over a subset `S` of size `t`, computed modulo `q`:

```
lambda_j(S) = product over i in S, i != j of  i * inverse(i - j) mod q
```

Signing keys are Ed25519 via the `cryptography` library: one presiding officer key and `a` party agent keys, all independent. Public keys are published on the board as 64-character lowercase hex of the 32-byte raw public key.

## 7. Ballot construction

A vote for candidate `j` is a vector of `m` independent ciphertexts, one per candidate, encrypting `1` at position `j` and `0` everywhere else.

```
for i in 0..m-1:
    v_i = 1 if i == j else 0
    r_i <- uniform in [1, q)                    see section 10 for the commitment
    alpha_i = g^{r_i} mod p
    beta_i  = pk^{r_i} * g^{v_i} mod p
```

`r_i` excludes zero. At `r_i = 0` the ciphertext is `(1, g^{v_i})` and the vote is readable directly off the board by anyone, with no key. This is a privacy failure available to compromised firmware at no cost and with no effect on any proof, so the verifier rejects it explicitly in section 8.3 rather than trusting the prover's sampling.

Exponential ElGamal is used because ciphertexts multiply componentwise into an encryption of the sum. Decryption recovers `g^T`, not `T`, and `T` is recovered by search. With this encoding `T` is bounded by the ballot count, so the search is trivial. This is the reason the vector encoding is used rather than packing the candidate index into a single ciphertext.

A ballot record carries `m` ciphertexts, `m` validity proofs, and one sum-to-one proof.

`ballot_serial` is per booth, starts at 1, and increases by exactly 1 for every ballot issued, including ballots that are subsequently spoiled. Serials are never reused and never skipped. A gap in the serial sequence is a rejection condition.

## 8. Validity proof, per candidate

This is the two-branch disjunctive sigma protocol of Cramer, Damgard and Schoenmakers, made non-interactive by Fiat-Shamir. It proves that `(alpha, beta)` encrypts `0` or encrypts `1`, without revealing which.

Branch 0 is the statement `log_g(alpha) = log_pk(beta)`. Branch 1 is the statement `log_g(alpha) = log_pk(beta * g^{-1})`.

### 8.1 Prover

Let `v` be the true value, `d = 1 - v` the simulated branch, `r` the encryption randomness.

Simulated branch `d`:

```
c_d <- uniform in [0, q)
f_d <- uniform in [0, q)
target_d = beta * (g^d)^{-1} mod p
a_d = g^{f_d}  * alpha^{-c_d}    mod p
b_d = pk^{f_d} * target_d^{-c_d} mod p
```

Real branch `v`:

```
w <- uniform in [0, q)
a_v = g^w  mod p
b_v = pk^w mod p
```

Challenge, then the split, then the response:

```
c   = B2I(SHA-256(preimage below)) mod q
c_v = (c - c_d) mod q
f_v = (w + c_v * r) mod q
```

The whole soundness of the scheme is that the prover chooses one sub-challenge freely and the other is forced. A construction in which both `c_0` and `c_1` are chosen freely makes forgery trivial. Check this against the Cramer, Damgard and Schoenmakers paper on paper before accepting any generated code, and check it against the independent re-derivation recorded in section 19.

The published proof is `(c_0, c_1, f_0, f_1, a_0, b_0, a_1, b_1)`.

`c_1` is redundant given `c` and `c_0`. Both are published anyway, and the verifier checks the sum. This is deliberate: it makes the failure mode visible rather than silently absorbed.

### 8.2 Challenge preimage

```
challenge for validity proof, candidate index i, ballot serial s =
SHA-256(
    L("EVOTE-VALIDITY-v1")           32 bytes
    Q                                32 bytes
    S32(booth_id)                    32 bytes
    U64(ballot_serial)                8 bytes
    U64(candidate_index)              8 bytes
    I2B(pk)                         384 bytes
    I2B(alpha_i)                    384 bytes
    I2B(beta_i)                     384 bytes
    I2B(a_0)                        384 bytes
    I2B(b_0)                        384 bytes
    I2B(a_1)                        384 bytes
    I2B(b_1)                        384 bytes
)
reduced modulo q
```

Total preimage length is exactly 2800 bytes.

`Q` carries the candidate list and the public key, so a proof cannot be replayed into a different election or a different candidate list. `booth_id`, `ballot_serial` and `candidate_index` are carried explicitly, so a proof cannot be moved to another booth, another ballot, or another position in the same ballot. This is strong Fiat-Shamir. Omitting any of these gives weak Fiat-Shamir, and the paper's citation of Bernhard, Pereira and Warinschi then becomes a description of our own defect.

### 8.3 Verifier

In order, rejecting on the first failure:

1. `in_group(alpha_i)`, `in_group(beta_i)`, `in_group(a_0)`, `in_group(b_0)`, `in_group(a_1)`, `in_group(b_1)`.
2. `alpha_i != 1`. This is the encryption randomness being zero, which publishes the vote in clear. It applies to the ciphertext components only, never to `a_0`, `b_0`, `a_1`, `b_1`, where the identity is a legitimate value.
3. `0 <= c_0, c_1, f_0, f_1 < q`.
4. Recompute `c` from the preimage in 8.2.
5. `(c_0 + c_1) mod q == c`.
6. `g^{f_0} == a_0 * alpha_i^{c_0} mod p`.
7. `pk^{f_0} == b_0 * beta_i^{c_0} mod p`.
8. `g^{f_1} == a_1 * alpha_i^{c_1} mod p`.
9. `pk^{f_1} == b_1 * (beta_i * g^{-1})^{c_1} mod p`.

Check 5 is the one that carries the soundness of the whole scheme. Checks 6 through 9 pass for a forged proof in which the prover chose both sub-challenges freely. Removing check 5 leaves every honest-path test passing.

## 9. Sum-to-one proof

The per-candidate proofs establish that each entry is `0` or `1`. They do not establish that exactly one entry is `1`. That is what this proof is for. Without it a ballot of all ones passes every validity proof.

Let

```
A = product of alpha_i over i in 0..m-1   mod p
B = product of beta_i  over i in 0..m-1   mod p
R = sum of r_i over i in 0..m-1           mod q
```

If the ballot is well formed then `A = g^R` and `B = pk^R * g^1`, so `B * g^{-1} = pk^R`. The proof is a Chaum-Pedersen equality of discrete logarithms for bases `(g, pk)` and targets `(A, B * g^{-1})`.

### 9.1 Prover

```
w <- uniform in [0, q)
a = g^w  mod p
b = pk^w mod p
c = B2I(SHA-256(preimage below)) mod q
f = (w + c * R) mod q
```

Published as `(c, f, a, b)`.

### 9.2 Challenge preimage

```
challenge for sum-to-one proof, ballot serial s =
SHA-256(
    L("EVOTE-SUMONE-v1")             32 bytes
    Q                                32 bytes
    S32(booth_id)                    32 bytes
    U64(ballot_serial)                8 bytes
    I2B(g)                          384 bytes
    I2B(pk)                         384 bytes
    I2B(A)                          384 bytes
    I2B(B_over_g)                   384 bytes
    I2B(a)                          384 bytes
    I2B(b)                          384 bytes
)
reduced modulo q
```

Total preimage length is exactly 2408 bytes. `B_over_g` is `B * g^{-1} mod p`, computed by the verifier from the published ciphertexts rather than read from the board.

### 9.3 Verifier

The verifier recomputes `A` and `B` from the ballot's own ciphertexts. It never reads them from the record. Then:

1. `in_group` on `A`, `B_over_g`, `a`, `b`.
2. `0 <= c, f < q`.
3. Recompute `c` and compare.
4. `g^f == a * A^c mod p`.
5. `pk^f == b * B_over_g^c mod p`.

## 10. Pre-poll commitments and the test schedule

### 10.1 Randomness commitments

Before the poll opens, the machine draws a randomness vector for every ballot serial it may issue, `1` to `ballots_expected`, and publishes a commitment to each. The vector is fixed to a serial, not to a candidate choice, so the machine is committed to its randomness before it learns what the voter selects. This is what makes vote redirection detectable at a challenged ballot rather than merely improbable.

```
K_s = SHA-256(
        L("EVOTE-RCOMMIT-v1")        32 bytes
        Q                            32 bytes
        S32(booth_id)                32 bytes
        U64(ballot_serial)            8 bytes
        I2B(r_0) .. I2B(r_{m-1})    384 * m bytes
        nonce_s                      32 bytes
      )
```

Total length `136 + 384m`, which is 2440 bytes for `m = 6`. `nonce_s` is 32 random bytes, kept secret until the record is opened.

The board carries `K_s` for every serial in `1..ballots_expected`, published in the pre-poll section and covered by the digest and the signatures.

### 10.2 Test schedule commitment

The test schedule is drawn before the poll from a seed, and the seed is committed before the poll and revealed at close. A schedule decided live by the tester cannot be audited and gives adversary A3 nothing coherent to partially leak.

```
T = SHA-256(
      L("EVOTE-TESTSCHED-v1")        32 bytes
      Q                              32 bytes
      S32(booth_id)                  32 bytes
      schedule_seed                  32 bytes
      U64(test_rate.num)              8 bytes
      U64(test_rate.den)              8 bytes
    )
```

Total length 144 bytes.

Derivation of the schedule, for each serial `s`:

```
draw_s = B2I( SHA-256( L("EVOTE-TESTDRAW-v1") || schedule_seed || U64(s) )[0:8] )
s is scheduled as a test ballot  iff  draw_s * test_rate.den < test_rate.num * 2^64
```

Only the first 8 bytes of the digest are used, interpreted big-endian. The comparison is exact integer arithmetic with no floating point.

At poll close, `schedule_seed` is published. The verifier recomputes `T`, recomputes the schedule, and checks that the set of spoil records matches the schedule exactly. A machine that skipped a scheduled challenge is caught here.

## 11. Spoil records

When a scheduled test ballot is challenged, the machine reveals the randomness vector and the selected candidate index. The ballot is excluded from the tally.

Verification of one spoil record:

1. Re-encrypt: for every `i`, compute `alpha_i' = g^{r_i}` and `beta_i' = pk^{r_i} * g^{v_i}` where `v_i` is `1` at the opened index and `0` elsewhere. Every one of the `2m` components must equal the published ciphertext. One mismatch anywhere is a failure of the whole record.
2. Recompute `K_s` from the revealed vector and nonce and compare against the pre-poll commitment.
3. Confirm the serial appears in the recomputed test schedule.
4. Confirm the serial's ciphertexts are excluded from every candidate aggregate.

A spoiled ballot's validity proofs are still checked in the ordinary way. A spoiled ballot is still counted in the poll register.

### 11.1 The tester's comparison (revision 3)

A machine that redirects a vote and is then challenged has two choices. If it opens a candidate other than the one it encrypted, check 1 fails and the board alone shows it. If it opens truthfully, every record on the board is consistent, and the only evidence is that the opened index differs from what the tester pressed. That comparison is made by the tester at the booth, in the standard Benaloh challenge: the machine displays the opened candidate index, and the tester checks it against their own selection before the ballot is spoiled.

The tester's selection is not written to the board. The machine writes the board, so a compromised machine would write a selection that matches what it opened. A tester mismatch is a P3 failure attributed to the spoil record for that serial.

In simulated runs the harness plays the tester and supplies the comparison to the verifier as a map from ballot serial to the selected candidate index. A board verified without that map establishes check 1 to 4 only, and cannot detect a redirecting machine that opens truthfully. The paper states this.

## 12. Poll register

Written at poll close by basket A, covered by the digest and the signatures.

```
ballots_issued    every serial handed out, including spoiled
ballots_spoiled   count of spoil records
ballots_counted   ballots_issued - ballots_spoiled
```

The verifier checks that `ballots_counted` equals the number of ballot records included in the aggregate, that serials run from 1 to `ballots_issued` with no gap and no repeat, and that `ballots_spoiled` equals the number of spoil records. This is the check that catches ballot stuffing, because it is a count produced independently of the ciphertexts.

## 13. Aggregation and threshold decryption

### 13.1 Aggregation

For each candidate index `i`, over all ballot serials not present in the spoil set:

```
A_i = product of alpha_{s,i}  mod p
B_i = product of beta_{s,i}   mod p
```

The verifier recomputes both from the published ballots. The published aggregate is a convenience and is never trusted.

### 13.2 Partial decryption

Trustee `j` in the decrypting subset `S`, `|S| = t`, publishes for each candidate `i`:

```
M_{j,i} = A_i^{s_j} mod p
```

with a Chaum-Pedersen proof that the exponent used is the same `s_j` committed in `h_j`. Bases `(g, A_i)`, targets `(h_j, M_{j,i})`.

```
w <- uniform in [0, q)
a = g^w      mod p
b = A_i^w    mod p
c = B2I(SHA-256(preimage below)) mod q
f = (w + c * s_j) mod q
```

```
challenge for partial decryption proof, trustee j, candidate i =
SHA-256(
    L("EVOTE-PARTIAL-v1")            32 bytes
    Q                                32 bytes
    U64(trustee_index)                8 bytes
    U64(candidate_index)              8 bytes
    I2B(g)                          384 bytes
    I2B(A_i)                        384 bytes
    I2B(h_j)                        384 bytes
    I2B(M_{j,i})                    384 bytes
    I2B(a)                          384 bytes
    I2B(b)                          384 bytes
)
reduced modulo q
```

Total preimage length is exactly 2384 bytes.

Verifier: `in_group` on all six elements, range checks, recompute `c`, then `g^f == a * h_j^c mod p` and `A_i^f == b * M_{j,i}^c mod p`.

### 13.3 Combination and tally recovery

```
combined_i = product over j in S of  M_{j,i}^{lambda_j(S)}   mod p
g_to_T_i   = B_i * combined_i^{-1}  mod p
```

`T_i` is recovered from `g_to_T_i` by baby-step giant-step over the range `0` to `ballots_counted`. The verifier checks that the recovered `T_i` equals the declared tally, and separately that the sum of all `T_i` equals `ballots_counted`. A tally whose components are individually plausible but do not sum correctly is a rejection.

### 13.4 Decryption transcript

The transcript is the ordered record of everything needed to replay the decryption without any secret. It is a board record, not a log file.

```json
{
  "record_type": "decryption_transcript",
  "subset": [1, 3, 5],
  "lagrange_coefficients": {"1": "HEX384", "3": "HEX384", "5": "HEX384"},
  "partials": [
    {
      "trustee_index": 1,
      "candidate_index": 0,
      "partial": "HEX384",
      "proof": {"c": "HEX384", "f": "HEX384", "a": "HEX384", "b": "HEX384"}
    }
  ]
}
```

`partials` is ordered by `trustee_index` then `candidate_index`, ascending, with no gaps. The verifier recomputes the Lagrange coefficients itself and compares against the published ones rather than using them.

## 14. Bulletin board record schemas

The board is a single JSON object. Top-level keys, all mandatory:

```
election_config      the configuration of section 5.1 without `seed`
base_hash            64-character lowercase hex of Q
trustee_setup        pk, commitments, n, t (no record_type)
authority_keys       officer and agent Ed25519 public keys, k
```

## 15. Canonical serialisation, digest and signatures

### 15.1 Canonical bytes

```python
canonical = json.dumps(board, sort_keys=True, separators=(",", ":"),
                       ensure_ascii=True).encode("utf-8")
```

Sorted keys, no whitespace, ASCII escaped. Array order is significant and is fixed by section 14. Round-tripping is a required test: serialise, parse, serialise again, and the two byte strings must be identical. If they are not, the verifier computes a different digest and nothing validates.

### 15.2 Digest

```
D = SHA-256( L("EVOTE-BOARD-v1") || canonical )
```

`D` is 32 raw bytes, published as 64-character lowercase hex.

### 15.3 Signatures

The Ed25519 message is:

```
message = L("EVOTE-SIG-v1") || D          exactly 64 bytes
```

The signature file is separate from the board file and has this shape:

```json
{
  "digest": "64-char hex",
  "officer_signature": "128-char hex",
  "agent_signatures": [{"agent_index": 0, "signature": "128-char hex"}]
}
```

Acceptance requires a valid officer signature plus at least `k` valid agent signatures from distinct agents whose public keys appear in `authority_keys`. A signature from a key not on that list is not counted and its presence is itself a rejection condition.

### 15.4 Export

The exported artefact is the board file plus the signature file. Nothing else crosses the air gap. Before export, the exporter scans the output for anything share-shaped and fails on a hit. Trustee shares, the polynomial coefficients, `sk`, the machine's private attack log and any per-ballot timing data must not appear.

## 16. Verifier check order and property attribution

The verifier outputs `Accept`, or `Reject` together with the property that failed and the record that caused it. Five properties, in this order.

**P1 board integrity.** Canonical re-serialisation matches, digest recomputes, officer signature valid, at least `k` distinct valid agent signatures, all signing keys on the published list, `Q` recomputes from the published parameters.

**P2 ballot well-formedness.** Every ballot has exactly `m` ciphertexts in order, every group element is in `G`, every validity proof passes section 8.3, every sum-to-one proof passes section 9.3.

**P3 cast-as-intended.** Every spoil record passes section 11, including the tester's comparison of section 11.1 where the tester's selections are supplied. The set of spoil records equals the schedule recomputed from the revealed seed. Every spoiled ballot is excluded from the aggregate.

**P4 ballot-count integrity.** Serials run 1 to `ballots_issued` with no gap or repeat, register counts are internally consistent, the number of ballots entering the aggregate equals `ballots_counted`, and every published randomness commitment corresponds to an issued serial.

**P5 tallied-as-recorded.** Aggregates recompute from the published ciphertexts, every partial decryption proof passes, Lagrange coefficients recompute, the combination yields the declared tally, and the tally sums to `ballots_counted`.

Attribution is a reported metric, so it has to be right. The mapping from the attack corpus to the expected property is:

```
vote redirection            (basket A)   P3
ballot stuffing             (basket A)   P4
malformed ballot injection  (basket B)   P2
tally manipulation          (basket C)   P5
retroactive board edit      (basket C)   P1
```

A verifier that names P5 when the attack was a retroactive board edit is a bug, not a near miss.

Ordering note. P1 runs first because a board that fails integrity cannot be reasoned about at all. P3 runs before P5 because vote redirection leaves the tally internally consistent, and a verifier that reaches the tally check first will report the wrong property.

Clean-mode false rejection must be exactly zero. If one clean election is rejected, everything stops until it is found, because a verifier with false positives makes every detection number in the paper meaningless.

## 18. Deliberate simplifications, to be stated in the paper

1. Trusted dealer instead of distributed key generation. Nothing the verifier checks depends on how the shares were produced.
2. Single-booth elections in the cryptographic pipeline. Multi-booth behaviour is simulated in the harness for the C0 cluster-sampling baseline, not run end to end.
3. Finite-field ElGamal rather than elliptic curve, chosen for auditability of the arithmetic. The performance cost is reported rather than hidden.
4. The challenge and spoil flow assumes a tester who follows the schedule. A tester who is themselves compromised is outside the threat model and is named as such.

### 21.1 Verbatim

1. ## 1. Challenge-splitting equation

**Setting.** Group $G = \langle g\rangle$ of prime order $q$ (inside $\mathbb{Z}_p^*$ or an elliptic curve group); public key $h = g^x$; ciphertext $(a,b) = (g^r,\; h^r\cdot m_\beta)$ with $m_\beta \in \{m_0, m_1\}$ known and public. Branch $i \in \{0,1\}$ is the statement

$$\mathrm{DH}(g,h,a,b\cdot m_i^{-1}) \;:\; \log_g a = \log_h (b\, m_i^{-1}) = r,$$

each proved by the Chaum–Pedersen Σ-protocol (commitment $(u_i,v_i)$, challenge $c_i$, response $s_i$; verification $g^{s_i} = u_i a^{c_i}$ and $h^{s_i} = v_i (b\,m_i^{-1})^{c_i}$). Both branches share the challenge set $\mathbb{Z}_q$, which is the CDS94 §2 precondition for composition.

**Construction (CDS94, §3, the secret-sharing-based composition; correctness/WI and knowledge-extraction given by Theorem 8 of the CRYPTO'94 proceedings version — theorem numbering differs in some reprints, the referent is the general access-structure theorem, here instantiated at $n=2$, $t=1$).** The overall challenge $c$ is *shared* among the branches by a scheme whose *dual* is the 1-out-of-2 access structure: the shares held by any single (unqualified) branch must leave $c$ uniformly undetermined. At $n=2$ this is the additive / degree-1 Shamir scheme over the field $\mathbb{Z}_q$.

Let $\beta \in \{0,1\}$ be the branch for which the prover holds the witness $r$, and $\bar\beta = 1-\beta$.

- **Untaken branch $\bar\beta$ — sub-challenge chosen freely, *before* $c$ is known:**
$$c_{\bar\beta} \;\xleftarrow{\$}\; \mathbb{Z}_q, \qquad s_{\bar\beta} \;\xleftarrow{\$}\; \mathbb{Z}_q,$$
$$u_{\bar\beta} = g^{s_{\bar\beta}} a^{-c_{\bar\beta}}, \qquad v_{\bar\beta} = h^{s_{\bar\beta}} (b\, m_{\bar\beta}^{-1})^{-c_{\bar\beta}}$$
(i.e. the transcript $(u_{\bar\beta},v_{\bar\beta}, c_{\bar\beta}, s_{\bar\beta})$ is produced by the branch simulator on input $c_{\bar\beta}$, per the special honest-verifier ZK property invoked in CDS94 §2).

- **Taken branch $\beta$ — commitment honest:** $w \xleftarrow{\$} \mathbb{Z}_q$, $u_\beta = g^w$, $v_\beta = h^w$.

- **After the Fiat–Shamir challenge $c = H(\cdot) \bmod q$ is fixed, the sub-challenge for the taken branch is *derived*, not chosen:**
$$\boxed{\,c_\beta \;\equiv\; c \;-\; c_{\bar\beta} \pmod q\,}$$
and $s_\beta = w + c_\beta\, r \bmod q$.

- **The splitting equation the honest prover must satisfy, and the verifier checks:**
$$\boxed{\,c_0 + c_1 \;\equiv\; c \pmod q\,}$$

The modulus is $q$, the **prime order of the subgroup $\langle g\rangle$** (the exponent-group order / the order of the field over which the shares live) — *not* the modulus $p$ of the ambient group. In the general CDS form the check is $\sum_i \lambda_i c_i \equiv c \pmod q$ for the Lagrange coefficients $\lambda_i$ of the interpolation points; at $n=2$ with points $\{1,2\}$ mapped to the standard additive instantiation, $\lambda_0 = \lambda_1 = 1$, giving the boxed form. Soundness rests on the fact that a prover who can answer both $c_0$ and $c_1$ for two distinct overall challenges yields two accepting branch transcripts on one branch, from which the special-soundness extractor of Chaum–Pedersen recovers $r$; witness indistinguishability holds because $(c_0,c_1)$ is a uniform pair subject to $c_0+c_1=c$ regardless of $\beta$.

## 2. Fiat–Shamir hash preimage under strong binding

$c = H(\,\cdot\,) \bmod q$, where the preimage is the following values in exactly this order, under a fixed injective (length-prefixed or fixed-width) encoding, so that no two distinct statements can produce the same byte string:

1. **Domain separator / protocol tag**, including a version identifier and the name of this specific proof type — e.g. an ASCII label distinguishing "2-branch OR of Chaum–Pedersen over ElGamal" from every other proof in the system (prevents cross-protocol transplanting of a transcript).
2. **Group parameters**: the group identifier — $(p, q, g)$ for a prime-order subgroup, or the named-curve identifier together with $q$ and the encoding of $g$. $q$ must appear explicitly, since it is the modulus of the splitting equation.
3. **Context identifiers**, each as a separate length-prefixed field:
   - election / ceremony identifier,
   - contest (question) identifier,
   - ballot identifier or voter public credential,
   - the positional index of *this* ciphertext within the ballot/contest (prevents replaying a valid proof from one option slot into another),
   - any session, round, or trustee-set identifier that sco pes validity.
4. **Public key** $h$ (and, if the key is a combination of trustee shares, the canonical encoding of the combined key actually used, not the individual shares).
5. **Candidate/message list**: both admissible plaintexts in canonical order, $m_0$ then $m_1$, together with the index-to-message encoding rule. Both must be hashed even though only one is "chosen" — otherwise a proof is replayable against a statement with a different second candidate.
6. **Ciphertext**: $a$ then $b$, in that fixed order.
7. **Branch first-round commitments**, in fixed branch order: $u_0,\; v_0,\; u_1,\; v_1$.

The derived branch statements $b\,m_0^{-1}$ and $b\,m_1^{-1}$ need not be hashed separately, since they are deterministic functions of items 5–6 under the fixed encoding rule; if a deployment allows them to be transmitted rather than recomputed, they must be added immediately after item 6.

The sub-challenges $c_0, c_1$ and the responses $s_0, s_1$ are **excluded** from the preimage: $c_{\bar\beta}$ is committed to implicitly through $u_{\bar\beta}, v_{\bar\beta}$, and including either $c_i$ would make the verifier's recomputation of $c$ circular. Weak Fiat–Shamir — hashing only item 7, or items 6–7 — is precisely what permits statement-substitution replay; items 1–6 are the additional binding required.
